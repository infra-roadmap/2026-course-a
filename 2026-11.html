11月：Terraform入門①

コースA：AWS資格（SAA）取得コース

ここからは手作業ではなく、コードでインフラを構築する「Terraform」を学びます。教材はOracle公式の日本語チュートリアルを使用します。当初1ヶ月分だった内容を11月・12月の2ヶ月に分けて、じっくり進めます。また、9月から続けているSAA-C03「座学ロードマップ」（SAA-C03座学：週1〜1.5時間程度を基本とします。各週のExam Prepは、その週のテーマに関連する部分を中心に確認します。Black Beltを補助的に利用する週は、15〜30分程度を追加で見込んでください（Black Beltの使い方はこちら））をこの月も並行して進めます（Week9〜12、メイン学習時間とは別枠の目安です）。（この11月以降はTerraform管理用の環境です。9月のOCI基礎・操作体験用、10月のネットワーク手動構築用の環境とは学習段階ごとに別環境として扱います。）

💼 この月で実務的にできるようになること：Terraform・OCI CLIの環境構築を終え、OCIとの認証設定（Provider）を済ませたうえで、VCNをHCLコードとして書き起こし、init／fmt／validate／plan／applyという一連の流れを自分の手で回せるようになります。

📖 この月で出てくる用語

用語ひとことで言うともう少し詳しく
Terraformインフラをコードで作るツール「IaC（Infrastructure as Code）」の代表的なツールの1つ。手作業をコードに置き換える
HCLTerraformが使う専用の記述言語HashiCorp Configuration Languageの略。JSONに近いが、もう少し人間が書きやすい構文
ProviderTerraformが操作するクラウドの種類を指定する設定「OCIを操作します」という宣言をコードの先頭に書く
plan / apply変更内容の予告 / 実際の適用plan＝「これから何を作る/変えるか」の確認、apply＝実際に実行

WEEK 01目安 4〜4.5h

Terraform概要、環境構築（Terraform・OCI CLI）

🎯 このタスクのゴール
これから「コード」でインフラを再現していくための土台として、Terraform本体とOCI CLIをインストールし、コマンドが使える状態にする。
📚 使う教材
  • Oracle公式チュートリアル（日本語）「Terraformの設定」 https://docs.oracle.com/ja-jp/iaas/developer-tutorials/tutorials/tf-provider/01-summary.htm
🛠 具体的な手順
  1. PowerShell（またはコマンドプロンプト）を開く（スタートメニューで「PowerShell」と検索して起動。普段VS Codeを使っているなら内蔵のターミナル機能でもよい）。作業用フォルダに cd コマンドで移動してから、以降の操作を行う。
  2. Terraformをインストールする。 PowerShellを「管理者として実行」で開き、
    winget install HashiCorp.Terraform
    を実行する（wingetはWindows標準のパッケージ管理ツール）。インストール後、新しいPowerShellを開き直してterraform -versionでバージョンが表示されることを確認する。
  3. OCI CLIをインストールする。 次のリンクからWindows用MSIインストーラー（v3.95.0）を直接ダウンロードする：oci-cli-3.95.0-Windows-Server-Installer.msi。ダウンロードした.msiファイルをダブルクリックして実行し、インストーラーの画面の指示に従って進める（設定はすべて初期値のままでよい）。インストール後、新しいPowerShellを開き直してoci --versionでバージョンが表示されることを確認する（開き直さないとPATHが反映されず、コマンドが見つからないと表示される）。
⚠️ つまずきやすいポイント
  • 「Terraform」と「OCI CLI」は別物。TerraformはOCI CLIが作った認証情報（~/.oci/config）を裏側で利用する、という関係を理解しておくと混乱しにくい（実際に認証情報を作るのは来週）。
✅ 成果物
🧭 到達判定
  • TerraformとOCI CLIが別のツールであり、両者がどう関係するか説明できる
  • terraform -version／oci --versionでインストールを確認できる

WEEK 02目安 3.5〜4h

APIキー発行、Provider記述、疎通確認

🎯 このタスクのゴール
OCIコンソール側とローカル側の両方に鍵を登録して認証を通し、Terraformから「OCIを操作します」と宣言するprovider.tfを書く。
📚 使う教材
  • Oracle公式チュートリアル（日本語）「Terraformの設定」 https://docs.oracle.com/ja-jp/iaas/developer-tutorials/tutorials/tf-provider/01-summary.htm
🛠 具体的な手順
  1. APIキーを発行し、認証情報を設定する。 「準備→①→②→③」の順に進める。
    【準備】OCIDを2つ控える。 OCIコンソール右上のプロファイルアイコン→「自分のプロファイル」（旧表記は「ユーザー設定」）を開き、「OCID」の「コピー」でユーザーOCIDをメモ帳に貼って控える（ocid1.user.で始まる文字列）。テナンシーOCIDも、プロファイルメニュー内のテナンシー名の項目を開き、同様に控える（ocid1.tenancy.で始まる文字列。画面名が違って見つからない場合は「テナンシ」「OCID」で探す）。2つを取り違えないよう、メモ帳に「ユーザー：」「テナンシー：」と書き分けておく。
    ①ローカルで鍵ペアを作る。
    (1) PowerShellでTest-Path $HOME\.oci\configを実行する。Falseと表示されたら、次の(2)へ進む（初めて設定する場合はこちら）。Trueと表示されたら、設定ファイルがすでにあるので、先に下の「💡」の【config がすでにある場合】を読む。
    (2) oci setup configを実行する。最初に、手順の説明とドキュメントへのリンクが英語で表示されるが、質問ではないので読み飛ばす。
    (3) 続けて英語の質問が上から順に1つずつ表示されるので、次のように答える（貼り付けはPowerShell上で右クリック）。
    Enter a location for your config [C:\Users\<ユーザー名>\.oci\config]:
  → 何も入力せずEnter
Enter a user OCID:
  → 準備で控えた ocid1.user. で始まる値を貼り付けてEnter
Enter a tenancy OCID:
  → 準備で控えた ocid1.tenancy. で始まる値を貼り付けてEnter
Enter a region by index or name(e.g. ...):
  → リージョンの一覧が表示される。コンソール右上に表示されている自分のリージョン
    （東京なら ap-tokyo-1）の番号または名前を入力してEnter
Do you want to generate a new API Signing RSA key pair? ... [Y/n]:
  → Y と入力してEnter
Enter a directory for your keys to be created [...]:
  → 何も入力せずEnter
Enter a name for your key [oci_api_key]:
  → 何も入力せずEnter
Public key written to: C:\Users\<ユーザー名>\.oci\oci_api_key_public.pem
  → 質問ではなく、公開鍵を書き出したという表示。読み飛ばす
Enter a passphrase for your private key ("N/A" for no passphrase):
  → N/A と入力してEnter（Enterだけだと同じ質問が繰り返し表示される。
    パスフレーズを設定するとTerraform側で追加設定が必要になる）
    (質問の文言は、OCI CLIのバージョンで多少異なることがある。「[...]」の部分にはデフォルト値が表示される。)
    (4) 最後に、鍵ファイルや設定ファイルを書き出したことを示す英語のメッセージと、Fingerprintの行が表示されたら完了。dir $HOME\.ociを実行し、oci_api_key.pem（秘密鍵）、oci_api_key_public.pem（公開鍵）、config（設定ファイル）の3つがあることを確認する。Fingerprintの値は③の確認に使う（画面を閉じても、configファイルで後から確認できる）。秘密鍵は他人に渡さず、Gitにも入れない。
    ②公開鍵をOCIコンソールに登録する。 PowerShellでGet-Content $HOME\.oci\oci_api_key_public.pem | Set-Clipboardを実行して公開鍵の中身をコピーする（手順Bで鍵の名前を変えた場合は、そのファイル名に読み替える）。コンソールで「自分のプロファイル」→左側のリソース一覧「APIキー」→「APIキーの追加」を開き、「公開キーの貼付け」を選んで貼り付け、「追加」を押す。
    ③登録できたか確認する。 追加すると「構成ファイルのプレビュー」が表示される。その中のfingerprintが、ローカルの$HOME\.oci\config（メモ帳で開く：notepad $HOME\.oci\config）のfingerprintと一致していればOK（プロファイルを追加した場合は、そのプロファイルの欄の値と照合する）。
    この②を忘れると、①だけでは認証が通らない点に注意。
    💡 config がすでにある場合（①の(1)で True だった場合）

    以前に設定した、途中で中断した、などで config がすでにあると、oci setup config の最初の質問のあとに、次の2つが追加で表示される。

    Config file: ... already exists. Do you want add a profile here?
(If no, you will be prompted to overwrite the file) [Y/n]:
  → すでに config があるが、そこに設定（プロファイル）を追加するか。
    追加するなら Y、上書きするなら n（上書きでよいか再確認される）。Enterだけだと Y になる
Enter the name of the profile you would like to create:
  → 追加する設定（プロファイル）の名前。Y と答えた場合のみ表示される

    まず、既存の config が必要か判断する。 Get-Content $HOME\.oci\config で中身を見て、次のように分ける。
    ・空、覚えのない内容、過去に途中で止めた試行の残り → 不要（手順A）
    ・以前から使っている設定（別のテナンシーやユーザーの操作に使っているなど）→ 必要（手順B）
    判断に迷う場合は手順Bで進める（既存の設定を消さずに済むため）。

    手順A：既存の config が不要な場合（上書きする）
    A-1. 控えを取る。Copy-Item $HOME\.oci\config $HOME\.oci\config.bak
    A-2. oci setup config を実行し、設定ファイルの場所の質問はそのままEnter。
    A-3. Do you want add a profile here? の質問に n を入力する（Enterだけだとデフォルトの Y になるので、必ず n を打つ）。
    A-4. 上書きの確認が出たら許可する。
    A-5. 以降の質問は、①の(3)のとおりに答える（鍵のファイル名もEnterでよい。既存の鍵は上書きされる）。②③、疎通確認、provider.tf も本文のとおり進める。

    手順B：既存の config を残す場合（別のプロファイルとして追加する）
    B-1. 控えを取る。Copy-Item $HOME\.oci\config $HOME\.oci\config.bak
    B-2. dir $HOME\.oci で既存の鍵ファイル名（oci_api_key.pem など）を確認しておく。B-6で重複しない名前を付けるため。
    B-3. oci setup config を実行し、設定ファイルの場所の質問はそのままEnter。
    B-4. Do you want add a profile here? の質問に Y と答える。
    B-5. Enter the name of the profile you would like to create: には TERRAFORM と入力する（DEFAULT は使わない。大文字小文字も含めて覚えておく）。
    B-6. 以降の質問は、①の(3)のとおりに答える。ただし Enter a name for your key [oci_api_key]: には、既存の鍵と重複しない名前（例：oci_api_key_terraform）を入力する。Enterだけだとデフォルトの oci_api_key になり、既存の秘密鍵を上書きするおそれがある。
    B-7. 完了後、Get-Content $HOME\.oci\config で、[TERRAFORM] が追加されていること、既存のプロファイルの内容が変わっていないことを確認する。
    B-8. ②の公開鍵のコピーは、ファイル名を読み替えて Get-Content $HOME\.oci\oci_api_key_terraform_public.pem | Set-Clipboard を実行する。③の fingerprint は [TERRAFORM] の欄の値と照合する。
    B-9. 以降、疎通確認を含むOCI CLIのコマンドすべてに --profile TERRAFORM を付ける（例：oci iam compartment list --compartment-id <テナンシーOCID> --profile TERRAFORM）。provider.tf にも config_file_profile = "TERRAFORM" を追加する。

    すでに Y と答えて、プロファイル名の質問まで進んでしまった場合：手順Bで進めるなら、そのままB-5から続けてよい。手順Aにしたい場合は Ctrl+C で中断し、oci setup config を最初からやり直す（中断した場合は config は変更されていないはずだが、念のため Get-Content $HOME\.oci\config で中身が変わっていないか確認する）。

  2. CLIの疎通確認をする。 oci iam compartment list --compartment-id <テナンシーOCID>の<テナンシーOCID>を、準備で控えたテナンシーOCID（ocid1.tenancy.で始まる値。ocid1.user.ではない）に置き換えて実行し、認証設定が正しくできているかをOCI CLIから確認する（コンパートメント一覧がJSON形式で返ってくればOK）。プロファイルを分けた場合（手順B）は末尾に --profile TERRAFORM を付ける。エラーが出た場合は、下の「つまずきやすいポイント」を確認する。
  3. Providerを記述する。 作業フォルダにprovider.tfを作り、チュートリアルのサンプルをコピーして自分のテナンシーOCID等に書き換える。書き換える値（テナンシーOCID・ユーザーOCID・フィンガープリント・秘密鍵のパス・リージョン）は、いずれも$HOME\.oci\configに書かれている。秘密鍵のパスをコードに書くときは、Windowsでも\ではなく/区切りで書く（例："C:/Users/<ユーザー名>/.oci/oci_api_key.pem"。\のままだとHCLの文字列としてエラーになる）。プロファイルを分けた場合（手順B）は、プロバイダーの設定に config_file_profile = "TERRAFORM" も追加する。
⚠️ つまずきやすいポイント
  • oci setup configで鍵を作っただけでは認証は通らない。生成された公開鍵をOCIコンソール側にも登録する、という2段階セットであることを忘れないこと。
  • oci setup configの途中で「config がすでに存在する」という英語の質問が出ても、エラーではない。①の「💡」の【config がすでにある場合】に従って答える。
  • oci setup configで、パスフレーズの質問（Enter a passphrase for your private key）がEnterを押しても繰り返し表示される場合は、N/Aと入力する。
  • 疎通確認でNotAuthenticated（401）のようなエラーが出たら、②の登録漏れ、またはfingerprintの不一致を疑う。コンソールに表示された値とローカルのconfigの値を見比べる。
  • 鍵ファイルの権限に関する警告が出たら、oci setup repair-file-permissions --file $HOME\.oci\oci_api_key.pemを実行して権限を修正する。
  • OCIコンソールは表示言語を切り替えられる。本教材の項目名は日本語表示が前提。英語表示の場合は「My profile」→「API keys」→「Add API key」→「Paste public key」に読み替える。

WEEK 04目安 3.5〜4h

Resource基礎②（plan/applyでVCN構築）

🎯 このタスクのゴール
書いたコードをplanで確認したうえでapplyし、Terraformで管理する新しいVCNを作成する。10月に手動で作ったVCNには、Public/Private Subnet・NSG（public-nsg）・Route Table・Internet Gateway、さらに10月week3に作成したCompute（コンピュート）が紐づいて存在しており、これらを整理しないままVCNだけを削除しようとすると依存関係エラーになる（9月に作成したVCN・Computeは10月着手前にすでに削除済み）。手動で作ったSubnetは12月Week3、Computeは2月Week2でそれぞれTerraformコードとして個別に再構築する予定のため、この時点では手動のVCNとその中身はまだ削除せず、Terraform管理の新しいVCNを並行して作成するところまでを今週のゴールとする（一本化はSubnet・Computeの移行が完了したあと、段階的に行う）。
📚 使う教材
  • Oracle公式チュートリアル「インフラストラクチャの構築」 https://docs.oracle.com/ja-jp/iaas/developer-tutorials/tutorials/tf-provider/03-summary.htm
🛠 具体的な手順
  1. PowerShell（またはコマンドプロンプト）を開く（スタートメニューで「PowerShell」と検索して起動。普段VS Codeを使っているなら内蔵のターミナル機能でもよい）。作業用フォルダに cd コマンドで移動してから、以降の操作を行う。
  2. terraform planで「何が作られるか」の予告を確認する。
  3. terraform applyを実行し、yesと入力して、Terraform管理下の新しいVCNを作成する。
  4. 10月に手動で作ったVCNは、この時点ではまだ削除しない。 手動のVCNにはPublic/Private Subnet・NSG（public-nsg）・Route Table・Internet Gateway・Compute（10月week3作成分）がまだ紐づいており、依存リソースを持つVCNはそのままでは削除できない。これらのSubnet・Computeは12月・2月の学習でTerraformコードとして個別に再構築する予定のため、今週の時点で削除すると後続の週の前提が崩れる点に注意する（9月分のVCN・Computeは10月着手前にすでに削除済みのため、この時点でのVCNは10月の手動VCNとここで作成したTerraform管理VCNの2個であり、上限内に収まっている）。
⚠️ つまずきやすいポイント
  • terraform applyはいきなり実行せず、必ずplanで内容を確認してから実行する癖をつける。
  • OCIのVCNは、内部にSubnetなどの依存リソースが残っている状態では削除できない。「VCNを削除する」だけを覚えるのではなく、依存リソースを先に整理してから最後にVCN本体を削除する、という順序を意識しておく（実際に手動環境を片付けるのは、依存するSubnet・Computeの移行が完了したあと）。
📌 手動環境を最終的に片付けるときの考え方（参考）
12月にSubnet、2月にComputeがそれぞれTerraformコードで再構築された後、10月に手動で作ったVCNとその残り（NSG・Route Table・Internet Gateway）を片付ける際は、依存関係の内側から外側へ向かって次の順序で整理する。①10月時点の手動構築環境（VCN・Subnet・NSG・Route Table・Internet Gateway・Compute）を確認する。②Computeなど、稼働中で依存されているリソースを先に停止・削除する。③Subnet・NSG・Route Table・Internet GatewayなどVCNに依存するリソースを整理する。④依存関係が無くなったことを確認しながら、最後にVCN本体を削除する。⑤OCIコンソールで旧環境のリソースが残っていないことを確認する。⑥利用中のリソースがすべてTerraform管理下にある状態になっていることを確認する。
