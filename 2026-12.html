12月：Terraform実践

コースB：OCI限定コース（AWS資格を目指さない）

Terraformの基本操作をより実践的に理解し、Compute（コンピュート）まで含めた一連の構築ができるようにします。

💼 この月で実務的にできるようになること：terraform planの差分の読み方やtfstateの中身を理解した上で、data sourceで既存情報を参照しながらCompute環境までを一連のコードで構築・変更できるようになります。

📖 この月で出てくる用語

用語ひとことで言うともう少し詳しく
state管理Terraformの「現在の状態」を保存・確認することterraform state list等のコマンドで中身を見られる
data source既存の情報を参照する仕組み自分で作ったのではなく、OCI側に既にある情報（可用性ドメイン等）を取得して使う

WEEK 01目安 3.5h

terraform plan/apply の理解

🎯 このタスクのゴール
plan（予告）とapply（実行）の違いを、実際に差分を出して体感する。「コードを変えたとき」と「コンソールから直接変えたとき（ドリフト）」の2通りで差分を出し、terraform planの表示を自分で読めるようになる。
📚 使う教材
  • Terraform公式CLIドキュメント https://developer.hashicorp.com/terraform/cli
  • Terraform公式CLIドキュメント（terraform plan） https://developer.hashicorp.com/terraform/cli/commands/plan
🛠 具体的な手順
  1. PowerShell（またはコマンドプロンプト）を開く（スタートメニューで「PowerShell」と検索して起動。普段VS Codeを使っているなら内蔵のターミナル機能でもよい）。作業フォルダに移動してから、以降の操作を行う。
    cd $env:USERPROFILE\oci-learning-log
    PowerShellを開き直したら毎回、最初にこのcdを実行する（開き直した直後は別の場所にいる）。
  2. 今週使うものを確認する。 今週は新しいリソースは作らない。11月に作ったVCN（コード上の名前はoci_core_vcn.main、OCIコンソール上の名前はtf-vcn）の名前だけを変えて、差分の出方を観察する。名前の変更は、VCNを作り直さずにその場で書き換えられる安全な変更なので、練習に向いている。
    注意：OCIコンソールには、10月に手動で作ったVCNと、Terraformで作ったtf-vcnの2つが並んでいる。今週触るのはtf-vcnの方だけ（手動で作った方は触らない）。
    Gitは、11月Week 4で切ったfeature/add-subnetsbranchのままでよい。今週はcommit・pushしない。
  3. 切り出し前の基準を作る。 次を実行し、No changes. Your infrastructure matches the configuration.と表示されることを確認する。これは「コードの内容と、OCI上の実際の状態が一致している」という意味で、この後の差分が「自分の変更によるもの」だと判断する基準になる。
    terraform plan
    「No changes」以外が表示された場合：
    ・Enter a value:と入力を求められた場合：Ctrl+Cで中断し、terraform.tfvarsが作業フォルダ直下にあるか（dir terraform.tfvars）を確認する。
    ・Missing required providerのようなエラーの場合：terraform initを実行してから、もう一度terraform planを実行する。
    ・401-NotAuthenticatedの場合：11月Week 1のprovider.tf／terraform.tfvarsの値（fingerprint・OCID・秘密鍵のパス）を見直す。
    ・差分（~など）が表示された場合：applyせず、terraform.tfvarsのvcn_display_nameがtf-vcnになっているか、OCIコンソールのVCN名がtf-vcnのままか（誰かが変更していないか）を確認する。
  4. planの表示の読み方を押さえる。 これから出てくる差分表示を読むための基礎知識。差分の行頭の記号は、次の意味を持つ。
    記号   意味
+      新しく作る
-      削除する
~      その場で変更する（作り直しではない）
-/+    いったん削除してから作り直す（要注意。VCNなら中身のSubnet等にも影響する）
    最終行のPlan: 1 to add, 2 to change, 0 to destroy.は「作成1件・変更2件・削除0件の予定」という集計。applyの前に、まずこの行のdestroyの数が想定どおりか（今回は0）を見る習慣をつける。
  5. コードを1行だけ変更する。 名前はterraform.tfvarsのvcn_display_nameで指定している（11月Week 3で変数に切り出した）。notepad terraform.tfvarsで開き、次の1行だけを書き換えて保存する。
    （変更前） vcn_display_name = "tf-vcn"
（変更後） vcn_display_name = "tf-vcn-v2"
    半角の"で囲む点と、他の行は触らない点に注意。保存したら、次の2つを順に実行する。
    terraform fmt terraform validate
    Success! The configuration is valid.と表示されればOK（fmtは何も表示されなくても正常）。validateは文法のチェックだけで、OCIには接続しない。plan／applyの前に毎回行う習慣にする。
  6. planで差分を出す。 次を実行する。
    terraform plan
    次のような表示になれば成功（細かい表示はバージョンで多少異なる）。
      # oci_core_vcn.main will be updated in-place
  ~ resource "oci_core_vcn" "main" {
      ~ display_name = "tf-vcn" -> "tf-vcn-v2"
        id           = "ocid1.vcn.oc1.ap-tokyo-1.xxxx"
        # (xx unchanged attributes hidden)
    }

Plan: 0 to add, 1 to change, 0 to destroy.
    読み方：
    ・will be updated in-place＝作り直しではなく、その場で変更する。
    ・~ display_name = "tf-vcn" -> "tf-vcn-v2"＝->の左が今の値、右が変更後の値。コード（tfvars）の1行の変更が、ちゃんと差分として検出されている。
    ・Plan: 0 to add, 1 to change, 0 to destroy.＝変更1件のみ、削除は0件。
    ・unchanged attributes hiddenのように省略された部分は、変更がない項目。
    -/+やmust be replaced、destroyが1以上になっていたら、applyせず、手順5で書き換えた行を元（tf-vcn）に戻す。
    ここで、OCIコンソールの「ネットワーキング」→「仮想クラウド・ネットワーク」を開き直して（ブラウザを再読み込みして）VCN名を見る。まだtf-vcnのままのはず。planは「予告」を表示するだけで、OCIには何も変更を加えていない。
  7. applyで実際に変更する。 次を実行する。
    terraform apply
    planと同じ差分が表示され、Do you want to perform these actions?と確認を求められるので、yesと入力してEnterを押す（yes以外を入力すると中止される。applyは実行の直前にもう一度planを行い、その内容で確認を求める仕組み）。Apply complete! Resources: 0 added, 1 changed, 0 destroyed.と表示されれば成功。
    OCIコンソールのVCN一覧を再読み込みし、名前がtf-vcn-v2に変わっていることを確認する。これで「plan＝予告（何も変わらない）」「apply＝実行（実際に変わる）」の違いを確認できた。
  8. コードを元に戻す。 Terraformでは、変更を元に戻すのも同じ手順で行う。notepad terraform.tfvarsで開き、手順5で書き換えた行を元のvcn_display_name = "tf-vcn"に戻して保存する。次を順に実行する。
    terraform fmt terraform validate terraform plan
    今度は~ display_name = "tf-vcn-v2" -> "tf-vcn"、Plan: 0 to add, 1 to change, 0 to destroy.と表示される（->の左が現在の値、右がコードの値、という読み方は同じ）。確認できたらterraform applyを実行し、yesを入力する。コンソールのVCN名がtf-vcnに戻ったことを確認し、最後にもう一度terraform planを実行してNo changes.になることを確認する（この状態に戻してから次の手順に進む）。
  9. 「ドリフト」を体験する。 ここからは、コードは一切変更せず、OCIコンソール側だけを変更する。
    (1) OCIコンソールの「ネットワーキング」→「仮想クラウド・ネットワーク」を開き、tf-vcnをクリックして詳細画面を開く。
    (2) 詳細画面の「編集」ボタン（見つからない場合は「その他のアクション」メニューの中）を押し、名前をtf-vcn-console-editに書き換えて保存する。
    (3) 画面を再読み込みして、VCN名がtf-vcn-console-editに変わっていることを確認する。
    (4) PowerShellで次を実行する（terraform.tfvarsは触っていないので、コード上の名前はtf-vcnのまま）。
    terraform plan
    コードには何も書いていないのに、次のような表示が出る。
    Note: Objects have changed outside of Terraform

  # oci_core_vcn.main has changed
  ~ resource "oci_core_vcn" "main" {
      ~ display_name = "tf-vcn" -> "tf-vcn-console-edit"
        # (xx unchanged attributes hidden)
    }
（中略）
  # oci_core_vcn.main will be updated in-place
  ~ resource "oci_core_vcn" "main" {
      ~ display_name = "tf-vcn-console-edit" -> "tf-vcn"
        # (xx unchanged attributes hidden)
    }

Plan: 0 to add, 1 to change, 0 to destroy.
    読み方：
    ・上のNote: Objects have changed outside of Terraformのブロック＝「前回のapplyのあとに、Terraformの外（コンソール）で値が変えられていた」という検出結果。
    ・下のwill be updated in-placeのブロック＝「コードの内容に戻すために、これから変更する予定」。->の右のtf-vcnがコードの値。
    これが「ドリフト」（コードと実際の状態のズレ）。Terraformはplanのたびに、OCI上の実際の状態を読みに行ってコードと比べているため、コンソールから直接変更した内容も検出できる。実務では、コンソールからの手動変更がこのようにコードとのズレを生むため、Terraformで管理しているリソースはコンソールから直接触らない。
  10. applyでコード側の状態に戻す。 次を実行し、yesと入力する。
    terraform apply
    Apply complete! Resources: 0 added, 1 changed, 0 destroyed.と表示されたら、OCIコンソールを再読み込みして、VCN名がtf-vcnに戻っていることを確認する。コンソールで変えた内容が、コードの内容で上書きされたことになる。
  11. 最後に状態を確認する。 次を実行し、No changes. Your infrastructure matches the configuration.と表示されることを確認する。
    terraform plan
    あわせて、notepad terraform.tfvarsでvcn_display_name = "tf-vcn"になっていること、OCIコンソールのVCN名がtf-vcnであることを確認する（tf-vcn-v2やtf-vcn-console-editが残っていないこと）。
⚠️ つまずきやすいポイント
  • terraform applyの前に、必ずplanの最終行（Plan: ○ to add, ○ to change, ○ to destroy.）を見る。今週の変更はVCNの名前だけなので、想定は0 to add, 1 to change, 0 to destroy。destroyが1以上、または-/+・must be replacedが出た場合は、applyせずにコードを元に戻す（VCNが作り直されると、11月に作ったSubnetなどにも影響する）。
  • 手順5で書き換えたterraform.tfvarsを、元（tf-vcn）に戻し忘れない。tf-vcn-v2のままにすると、この先のWeekでも差分が出続ける。手順7で戻して「No changes」を確認しておくこと。
  • コンソールには2つのVCN（10月の手動作成分と、Terraformで作ったtf-vcn）が並んでいる。ドリフト体験で名前を変えるのはtf-vcnの方。間違えて手動作成分の名前を変えても、Terraformは何も検出しない。
  • ドリフトの手順で差分が出ない場合は、(a) コンソールでの名前の変更が保存されていない（画面を再読み込みして確認）、(b) terraform.tfstateのある作業フォルダ（oci-learning-log）以外でplanを実行している、のどちらかを疑う。なお、コードに書いていない項目（タグなど）は、コンソールで変更しても差分にならない場合がある。今回は、コードに書いてあるdisplay_nameを使うので差分が出る。
  • 実務でドリフトを見つけたときは、「コード側を実際の状態に合わせて直す」か「applyでコード側の状態に戻す」かを選ぶことになる。今回は、コードが正しい状態（正）なので、後者でコードの内容に戻した。どちらが正しいかを確認せずにapplyすると、必要な手動変更を消してしまうおそれがある。
  • terraform applyの確認でyes以外（yなど）を入力すると、何も実行されずに終了する。実行する場合は、半角でyesと入力する。
✅ 成果物
🧭 到達判定
  • planの差分の記号（+・-・~・-/+）の意味と、->の左右が何を表すか説明できる
  • planが「予告」で、applyが「実行」であることを、コンソールでVCN名が変わるタイミングの違いとあわせて説明できる
  • コード側を変更していないのにplanで差分が出る「ドリフト」が何によって起きるか説明できる
WEEK 02目安 4.5h

state管理

🎯 このタスクのゴール
Terraformが「今何を管理しているか」を自分で確認できるようになる。
📚 使う教材
  • Terraform公式ドキュメント（State） https://developer.hashicorp.com/terraform/language/state
🛠 具体的な手順
  1. PowerShell（またはコマンドプロンプト）を開く（スタートメニューで「PowerShell」と検索して起動。普段VS Codeを使っているなら内蔵のターミナル機能でもよい）。作業フォルダ（cd $env:USERPROFILE\oci-learning-log）に移動してから、以降の操作を行う。
  2. terraform.tfstateの中身をエディタで開いて構造（JSON形式）を確認する。
  3. terraform state listで管理対象のリソース一覧を表示する。
  4. terraform state show <resource>で特定リソースの詳細を確認する。
  5. OCI CLIとも突き合わせる。 oci compute instance list --compartment-id <コンパートメントOCID>を実行し、terraform state listの内容と実際に作成されているリソースが一致していることを確認する。
  6. 「なぜstateを直接編集してはいけないか」を理解する。 terraform apply実行後にフォルダ内へ自動生成されるterraform.tfstate.backup（1つ前の状態のバックアップ）の存在を確認し、これが「stateファイルは壊れやすく、手で編集するとコードと実際のリソースの対応が壊れる」ことへの保険であることをメモにまとめる。
⚠️ つまずきやすいポイント
  • tfstateには接続情報などの機密が平文で入ることがあるため、Gitには絶対に含めない（11月にすでに.gitignoreへ追加済みのはず）。
🧪 手動リソースのTerraform管理化（import）
Terraformを使わずに手動で作ったリソースをterraform importでstateに取り込み、コードと実際のリソースを一致させる。
  1. 手動でリソースを1つ作る。 OCIコンソールから、Terraformではまだ管理していない新しいNSG（例：manual-test-nsg）を1つ手動で作成する（Ingressルールは動作確認用にTCP 8080番を1つ追加する程度でよい）。
  2. コード側に受け皿を用意する。 main.tfに、作成したNSGと同じ内容（名前・所属VCN等）を指すresource "oci_core_network_security_group" "manual_test" {...}ブロックを追加する（この時点ではまだstateに紐づいていない）。
  3. importする。
    terraform import oci_core_network_security_group.manual_test <NSGのOCID>
    NSGのOCIDはOCIコンソールの詳細画面からコピーする。
  4. 一致を確認する。 terraform planを実行し、差分が（ほぼ）出ないことを確認する。差分が出た場合は、コード側の設定値が実際のリソースと食い違っているので、表示された差分を1つずつ実際の値に合わせて書き直す。
  5. 後片付けする。 確認できたら、手順2で追加したresource "oci_core_network_security_group" "manual_test" {...}ブロックをmain.tfから削除する。terraform planを再度実行し、このNSGが削除対象として表示されることを確認したうえで、terraform applyを実行して実体を削除する。コードとstateの両方から消すことで、次回以降のplanで再作成対象として残らないようにする。学習用に増やしたリソースはその都度整理する習慣をつける。
⚠️ つまずきやすいポイント
  • -targetオプションは、依存関係を無視するものではなく、指定したリソースを中心とした部分的なplan／apply／destroyを行うためのオプション。指定したリソースが依存する他のリソースは通常どおり考慮されるが、対象範囲を絞る分、コード全体の依存関係と実際に適用された状態がずれやすくなる。特にdestroy -targetで実体だけを削除すると、コードにはresourceブロックが残ったままになり、次回のplanで再作成対象として検出されてしまう（今回の後片付けでコードからブロックごと削除したのはそのため）。通常の運用では-targetなしのterraform plan／apply／destroyを基本とし、-targetは障害対応や復旧作業など、限定的な用途に絞って使う、という位置づけで覚えておく。
✅ 成果物
🧭 到達判定
  • tfstateを直接編集してはいけない理由を説明できる
  • terraform importで手動作成したリソースをTerraform管理下に置く流れを説明できる
WEEK 03目安 3.5h

data source、Computeまで含めた一連の構築

🎯 このタスクのゴール
既存の情報（可用性ドメイン）を参照しながら、Compute（コンピュート）インスタンスまでコードで構築する。
📚 使う教材
  • Terraform公式ドキュメント（Data Sources） https://developer.hashicorp.com/terraform/language/data-sources
🛠 具体的な手順
  1. PowerShell（またはコマンドプロンプト）を開く（スタートメニューで「PowerShell」と検索して起動。普段VS Codeを使っているなら内蔵のターミナル機能でもよい）。作業フォルダ（cd $env:USERPROFILE\oci-learning-log）に移動してから、以降の操作を行う。
  2. data "oci_identity_availability_domains" "ads" {}のようなdata sourceを定義し、可用性ドメインの一覧を取得する。
  3. Terraform apply前に、10月から使い続けている手動のCompute（Public Subnet、VM.Standard.E2.1.Micro）をOCIコンソールから削除する。 このあとTerraformで作成するComputeも同じE2.1.Microを使うため、手動作成分を残したままだと、テナンシー全体でのE2.1.Micro上限（最大2台）に抵触しうる。先に手動分を片付けてからapplyする。
  4. 取得した値を使ってoci_core_instanceリソースを記述する（subnet_idには11月に構築したTerraform管理VCNのPublic Subnetを指定する）。Shapeは、直前に削除した10月の手動Computeと同じVM.Standard.E2.1.Microにする。これにより「手動で作ったComputeを、同じ内容のままTerraformコードとして再構築する」という移行の流れを体験する。
  5. terraform fmtとterraform validateでコードを整形・検証してから、terraform applyでVCN〜Compute（コンピュート）までを一連の実行で構築できることを確認する。
✅ 成果物
🧭 到達判定
  • data sourceで取得した値を使ってComputeを構築できる
  • 手動作成分を先に削除してからapplyする必要がある理由を説明できる
WEEK 04目安 3h

Terraformコード拡張演習＆振り返り・学びメモ作成

🎯 このタスクのゴール
WEEK03で構築したCompute環境をvariableで拡張する小演習を行い、手を動かした状態のまま10〜12月をふりかえって自分の言葉で短くまとめる。公開記事を書くことが目的ではなく、「振り返って言語化する」こと自体が目的。
📚 使う教材
  • study-notesリポジトリ（9月に作成済み）。使い慣れたツール（Notion等）があればそちらでもよい https://github.com/
🛠 具体的な手順
  1. 作業用のbranchを切る。 11月に続き、変更はmainに直接コミットせずbranch上で行う。
    git checkout -b feature/second-instance
  2. 拡張演習：WEEK03で構築したCompute（コンピュート）環境に、variableを使って2台目のインスタンスを追加する（display_nameは1台目と別名にする）。2台目も同じVM.Standard.E2.1.Microとし、1台目と合わせてE2.1.MicroのAlways Free上限（テナンシー全体で最大2台）にちょうど収める。terraform fmt→terraform validateで整形・検証したあと、terraform planで追加分の差分だけが出ることを確認してからapplyする。
  3. 動作確認ができたら、Always Free枠を使い切らないよう2台目はterraform destroyで削除しておく（variable定義自体はコードに残してOK）。
  4. branch上でcommitし、pushする。
    git add . git commit -m "Add second instance variable" git push -u origin feature/second-instance
