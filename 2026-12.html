12月：Terraform入門②

コースA：AWS資格（SAA）取得コース

11月に続き、Terraformの基本文法を学びます。今月はVariable・Outputでハードコードした値を整理し、Subnetのコード化とGitでのバージョン管理を始めます。9月から続けているSAA-C03「座学ロードマップ」（SAA-C03座学：週1〜1.5時間程度を基本とします。各週のExam Prepは、その週のテーマに関連する部分を中心に確認します。Black Beltを補助的に利用する週は、15〜30分程度を追加で見込んでください（Black Beltの使い方はこちら））はこの月で完了します（Week13〜16、メイン学習時間とは別枠の目安です）。

💼 この月で実務的にできるようになること：CIDRやコンパートメントOCIDのような値をコードの外に切り出して管理し、Subnetのコード化と、GitHubでのコード管理を実務のIaC運用の基本として自分ひとりで回せるようになります。

📖 この月で出てくる用語

用語ひとことで言うともう少し詳しく

Output（出力値）applyの結果を画面に表示する仕組み作成したリソースのIDなどを、後から確認しやすくする
Git / .gitignoreコードのバージョン管理ツール／管理対象から除外するファイルの指定tfstateや秘密情報入りのファイルはGit管理から除外する

WEEK 01目安 3〜3.5h

Variable基礎（変数への切り出し）

🎯 このタスクのゴール
CIDRやコンパートメントOCIDのような値を、コードの外に切り出して管理できるようにする。切り出したあともterraform planが「No changes」のままであることで、動作を変えずに整理できたことを確認する。
🔐 識別子と秘密情報の違い
テナンシーOCID・ユーザーOCID・コンパートメントOCIDなどのOCIDは、リソースやアカウントを識別するための情報で、それ自体はパスワードのような秘密情報ではない。一方、API Key Private Key・Customer Secret Key・パスワード・トークンなどの認証情報は、漏洩すると不正利用につながる秘密情報にあたる。terraform.tfvars・.tfstate・.tfstate.backupには、こうした識別子や秘密情報が設定値として含まれることがあるため、内容にかかわらずGitへ不用意にコミットしないのが基本の習慣。
📚 使う教材
  • Oracle公式チュートリアル「変数の宣言」「出力値の照会」 https://docs.oracle.com/ja-jp/iaas/developer-tutorials/tutorials/tf-provider/04-summary.htm
🛠 具体的な手順
  1. PowerShell（またはコマンドプロンプト）を開く（スタートメニューで「PowerShell」と検索して起動。普段VS Codeを使っているなら内蔵のターミナル機能でもよい）。作業フォルダ（cd $env:USERPROFILE\oci-learning-log）に移動してから、以降の操作を行う。
  2. 切り出し前の基準を作る。 次を実行し、No changes. Your infrastructure matches the configuration.と表示されることを確認する。これは「11月にapplyして作ったVCNと、コードの内容が一致している」という意味で、この後の変数への切り出しが正しくできたかを判断する基準になる。
    terraform plan
    差分が出る場合は、11月のVCNのapplyが完了していない可能性があるので、先に11月の作業を終わらせる。あわせて、11月に疎通確認用として作ったcheck.tfが残っていれば、値を直接書いた古いファイルなので削除しておく。
    Remove-Item check.tf -ErrorAction SilentlyContinue
    （ファイルが無い場合は何も表示されず、それで正常）
  3. 何を変数にするかを確認する。 今回、コードに直接書いてある次の8つの値を変数に切り出す（5つはprovider.tf、3つはmain.tfにある）。まずnotepad provider.tfとnotepad main.tfで現在のコードを開き、直接書いてある値が下の表の8つであることを確認する。変数名は次のとおりに揃える（以降の手順でこの名前を使う）。
    変数名             いまの書き場所
tenancy_ocid       provider.tf の tenancy_ocid
user_ocid          provider.tf の user_ocid
fingerprint        provider.tf の fingerprint
private_key_path   provider.tf の private_key_path
region             provider.tf の region
compartment_id     main.tf の compartment_id
vcn_cidr_block     main.tf の cidr_block
vcn_display_name   main.tf の display_name
    仕組みは「variables.tf＝変数の宣言（名前と型だけ。値は書かない）」「terraform.tfvars＝実際の値（Terraformが自動で読み込む）」「.tfファイル＝var.変数名で値を呼び出す」の3点セット。
  4. variables.tfを作る（宣言）。 notepad variables.tfと入力して開き、「新しいファイルを作成しますか？」で「はい」を選ぶ（VS Codeでもよい）。次の内容を書いて保存する。
    variable "tenancy_ocid" {
  type        = string
  description = "Tenancy OCID"
}

variable "user_ocid" {
  type        = string
  description = "User OCID"
}

variable "fingerprint" {
  type        = string
  description = "API key fingerprint"
}

variable "private_key_path" {
  type        = string
  description = "Path to the API private key file"
}

variable "region" {
  type        = string
  description = "OCI region"
}

variable "compartment_id" {
  type        = string
  description = "Compartment OCID where the VCN is created"
}

variable "vcn_cidr_block" {
  type        = string
  description = "CIDR block of the VCN"
}

variable "vcn_display_name" {
  type        = string
  description = "Display name of the VCN"
}
    1つのvariable "名前" { ... }が変数1つの宣言。type = stringは「文字列の値を受け取る」という意味。default（初期値）は書いていないので、値はこの後のterraform.tfvarsなどから必ず渡す必要がある。（descriptionは説明文で、動作には影響しない。英語で書いているのは、メモ帳の保存形式による文字化けを避けるため）
  5. terraform.tfvarsを作る（実際の値）。 まず、現在の値を確認するため、notepad provider.tfとnotepad main.tfを開いておく（2つのウィンドウを並べると写しやすい）。そのうえでnotepad terraform.tfvarsを開いて新規作成し、現在provider.tf／main.tfに書いてある値と同じ値を次の形で書いて保存する。
    tenancy_ocid     = "ocid1.tenancy.oc1..xxxx"
user_ocid        = "ocid1.user.oc1..xxxx"
fingerprint      = "xx:xx:xx:...:xx"
private_key_path = "C:/Users/<ユーザー名>/.oci/oci_api_key.pem"
region           = "ap-tokyo-1"
compartment_id   = "ocid1.tenancy.oc1..xxxx"
vcn_cidr_block   = "10.0.0.0/16"
vcn_display_name = "tf-vcn"
    書き方は変数名 = "値"（値は半角の"で囲む）。xxxxや<ユーザー名>は例なので、必ず自分の実際の値に置き換える。値は手で打ち直さず、provider.tf／main.tfからコピーして貼り付ける（1文字違うだけで、後のplanで差分が出る）。ファイル名は必ずterraform.tfvarsにする（この名前だけ、Terraformが自動で読み込む）。保存後、dir terraform.tfvarsを実行して表示されることを確認する（terraform.tfvars.txtになっていたら、拡張子の.txtを外す）。
  6. provider.tfを変数に書き換える。 notepad provider.tfで開き、5つの値を次のようにvar.変数名に置き換えて保存する（値そのものはtfvarsに移したので、コードには書かない）。
    provider "oci" {
  tenancy_ocid     = var.tenancy_ocid
  user_ocid        = var.user_ocid
  fingerprint      = var.fingerprint
  private_key_path = var.private_key_path
  region           = var.region
}
    var.tenancy_ocidは「変数tenancy_ocidの値」を呼び出す書き方で、前後に"は付けない（付けると、var.tenancy_ocidという文字列そのものとして扱われる）。
  7. main.tfを変数に書き換える。 notepad main.tfで開き、VCNのブロックを次のように書き換えて保存する。
    resource "oci_core_vcn" "main" {
  compartment_id = var.compartment_id
  cidr_block     = var.vcn_cidr_block
  display_name   = var.vcn_display_name
}
    左側（compartment_idなど）はVCNリソースの属性名で変えない。右側だけをvar.変数名に変える。
  8. 切り出しが正しくできたか確認する。 次を順に実行する。
    terraform fmt terraform validate terraform plan
    validateがSuccess! The configuration is valid.になり、planが手順2と同じNo changes. Your infrastructure matches the configuration.になれば成功。「値の置き場所を変えただけで、中身は何も変わっていない」ことがplanで証明できる。
    ・-/+やmust be replaced、~の差分が出た場合：tfvarsの値が、最初にapplyしたときの値と違っている。applyせず（VCNが作り直されるおそれがある）、terraform state show oci_core_vcn.mainで実際の値を確認して、tfvarsを合わせ直す。
    ・Enter a value:と入力を求められた場合：tfvarsから値が渡っていない。Ctrl+Cで中断し、tfvarsのファイル名と、変数名のスペルが宣言と一致しているかを確認する。
  9. 変数の優先順位を体感する。 tfvarsは変更せず、コマンドで別の値を渡して、どちらが使われるかを確認する（PowerShellで次を実行）。
    terraform plan -var="vcn_display_name=tf-vcn-override"
    表示された差分の中で、display_name = "tf-vcn" -> "tf-vcn-override"のように、-varで渡した値に変わる予定になっていれば成功（Plan: 0 to add, 1 to change, 0 to destroy.）。tfvarsにはtf-vcnと書いてあるのに、-varの値が優先されたことが分かる。これは確認だけなので、applyはしない。確認後、terraform plan（-varなし）を実行し、No changes.に戻ることを確認する。優先順位は、弱い順に「default → 環境変数TF_VAR_名前 → terraform.tfvars → *.auto.tfvars → -var／-var-file」で、後に書いたものが勝つ。CI/CDや複数人開発で「どの値が実際に使われるか」を判断するときに必要な知識になる。
  10. 最後にファイルを確認する。 dir *.tf*を実行し、main.tf、provider.tf、variables.tf、terraform.tfvarsの4つがあることを確認する（outputs.tfは来週のWeek 2で扱う。check.tfは無くてよい）。
⚠️ つまずきやすいポイント
  • terraform.tfvarsには環境固有の値や、場合によっては秘密情報を含めるため、Gitでは絶対に管理しない（テナンシーOCID等のOCID自体はパスワードのような秘密情報ではないが、このファイルには秘密情報を含める可能性があるため、ファイル単位でGit管理対象から外す）。まだGitを導入していない状態だが（Git導入はWeek 4）、Week 4で.gitignoreを作ったら真っ先にこのファイルを登録すること。
  • var.xxxには"を付けない。region = "var.region"と書くと、リージョン名が「var.region」という文字列になり、エラーになる。
  • Reference to undeclared input variableと出たら、var.名前の名前がvariables.tfの宣言と違っている（スペルミス）か、宣言を書き忘れている。
  • Warning: Value for undeclared variableと出たら、terraform.tfvarsにあってvariables.tfに宣言が無い変数がある。名前のスペルを揃える。
  • 切り出しのあとのplanで-/+（作り直し）や~（変更）が出たら、applyしない。cidr_blockのように、変更するとVCNが作り直しになる値がある。作り直しになると、Week 3で作るSubnetなど、VCNにぶら下がるリソースにも影響する。
  • terraform.tfvarsは、作業フォルダ直下に置く。別のフォルダやterraform.tfvars.txtだと読み込まれず、Enter a value:と入力を求められる。

WEEK 02目安 4〜4.5h

Output（出力値の定義）、AWS実機ハンズオン②（IAM Role→EC2→S3・60〜90分）

🎯 このタスクのゴール
applyの結果得られる値を、あとから確認できるようにする。
📚 使う教材
  • Oracle公式チュートリアル「変数の宣言」「出力値の照会」 https://docs.oracle.com/ja-jp/iaas/developer-tutorials/tutorials/tf-provider/04-summary.htm
🛠 具体的な手順

  2. outputs.tfにVCNのOCIDを出力する設定を書き、terraform apply後に値が表示されることを確認する。
⚠️ つまずきやすいポイント
  • terraform.tfvarsには、テナンシーOCIDなどの識別子や、認証情報などの秘密情報が値として入る。OCID自体はパスワードのような秘密情報ではないが、ファイルの中身を個別に選別するのは煩雑なため、terraform.tfvarsごとGitでは管理しないのが基本。まだGitを導入していない状態だが（Git導入は再来週）、導入時に.gitignoreへ真っ先に登録すること。
✅ 成果物
🧭 到達判定
  • outputsが何のために使われる仕組みか説明できる
  • applyの結果として値が画面に表示されることを確認できる
🖥️ 追加ハンズオン：AWS実機タッチ②（IAM Role → EC2 → S3、60〜90分）
10月week4のAWS実機タッチ（VPC・Subnet・EC2）とは別に、SAAで頻出する「IAM Role → EC2 → S3」の権限委譲パターンを、AWS Consoleで実際に触って体験する。大規模な環境構築は行わず、Terraformでコード化する前にAWSの実体を確認することが目的。
🛠 具体的な手順
  1. 10月week4で作成したAWSアカウントでログインする（無料利用枠の期限内であることを確認）。
  2. IAM Roleを作成する。「IAM」→「ロール」→「ロールを作成」で、信頼されたエンティティに「AWSのサービス」→「EC2」を選び、許可ポリシーにAmazonS3ReadOnlyAccessをアタッチする。
  3. S3バケットを作成する。 バケット名は一意な名前にし、リージョンはEC2と合わせる。適当なテキストファイルを1つアップロードしておく。
  4. EC2インスタンスを起動する。 AMIは「Ubuntu Server」、インスタンスタイプはt3.microを選ぶ（作成前にコンソール上で「無料利用枠の対象」の表記があることを確認する）。「IAMロール」欄に手順2で作成したロールを指定する。セキュリティグループはSSH（22番）を自分のグローバルIPからのみ許可する。
  5. AWS CLIが使える状態か確認する。 Ubuntu ServerのAMIにはAWS CLIがプリインストールされていないことがあるため、SSH接続後まず
    aws --version
    を実行する。コマンドが見つからない場合は
    sudo apt update sudo apt install -y awscli
    でインストールし、再度aws --versionでバージョンが表示されることを確認する。
  6. IAM Roleによる認証を確認する。 アクセスキーは一切入力せず、
    aws sts get-caller-identity
    を実行し、IAM Role（Instance Profile）経由で認証された自分自身の情報（Account／Arn等）が表示されることを確認する。ここでAccess KeyやSecret Keyをインスタンス内に保存する操作は行わない。
  7. S3にアクセスする。 認証確認ができたら
    aws s3 ls aws s3 cp s3://バケット名/ファイル名 .
    を実行し、IAM Roleによる権限委譲だけでS3にアクセスできることを確認する。
  8. 確認できたらリソースを削除する。 EC2インスタンスを終了し、S3バケットも削除する。
✅ 成果物
🧭 到達判定
  • IAM Roleを使うことで、アクセスキーをEC2に埋め込まずS3へアクセスできる理由を説明できる

Subnet構築（Public/Private）

🎯 このタスクのゴール
10月に手動で作ったPublic/Private Subnetと同じ構成を、11月にTerraformで新規構築したVCN（10月の手動VCNとは別物）の中に、コードとして再現する。
📚 使う教材
  • Oracle公式チュートリアル「インフラストラクチャの変更」 https://docs.oracle.com/ja-jp/iaas/developer-tutorials/tutorials/tf-provider/05-summary.htm
🛠 具体的な手順
  1. PowerShell（またはコマンドプロンプト）を開く（スタートメニューで「PowerShell」と検索して起動。普段VS Codeを使っているなら内蔵のターミナル機能でもよい）。作業フォルダ（cd $env:USERPROFILE\oci-learning-log）に移動してから、以降の操作を行う。
  2. oci_core_subnetリソースをPublic/Privateの2つ分コード化する（vcn_idには11月WEEK04でapplyしたTerraform管理VCNのIDを指定し、10月の手動VCNは対象にしない）。applyする。
  3. CLIでも確認する。 oci network subnet list --compartment-id <コンパートメントOCID>を実行し、コンソールとCLIの両方でSubnetが作成されていることを確認する。
✅ 成果物
🧭 到達判定
  • Public/Private Subnetをコードで再現できる
  • コンソールとCLIの両方でリソースの存在を確認できる

Git管理開始

🎯 このタスクのゴール
ここまでのコードをGitHubで管理できるようにする。
📚 使う教材
  • Oracle公式チュートリアル「インフラストラクチャの変更」 https://docs.oracle.com/ja-jp/iaas/developer-tutorials/tutorials/tf-provider/05-summary.htm
🛠 具体的な手順
  1. PowerShell（またはコマンドプロンプト）を開く（スタートメニューで「PowerShell」と検索して起動。普段VS Codeを使っているなら内蔵のターミナル機能でもよい）。作業フォルダ（cd $env:USERPROFILE\oci-learning-log）に移動してから、以降の操作を行う。
  2. Gitをインストールする（未導入の場合）。 PowerShellで
    winget install Git.Git
    を実行する。インストール後、新しいPowerShellでgit --versionが表示されることを確認する。
  3. 作業フォルダをGitHubのリポジトリにつなぐ。 Terraformコードは9月week4で作成済みのoci-learning-logリポジトリに置く（新規リポジトリは作らない）。ここまでコードを書いてきた作業フォルダ（oci-learning-log）の中で、次の3つを順に実行する。git cloneは使わない（別の場所にフォルダができ、terraform.tfstateが置き去りになるため）。
    git init -b main git remote add origin https://github.com/<GitHubユーザー名>/oci-learning-log.git git pull origin main --allow-unrelated-histories
    GitHub上にある9月作成のREADME.mdが作業フォルダに取り込まれる（すでに別の場所へcloneしてしまった場合は、作業フォルダの中身をすべてcloneしたフォルダへ移し、以降はそのフォルダを作業フォルダとして使う。terraform.tfstateも忘れずに移す）。
  4. 作業フォルダ直下に.gitignoreを新規作成し、*.tfstate、*.tfstate.backup、terraform.tfvars、.terraform/を書く。そのうえで、ここまでのコードを最初のpushとしてmainブランチにpushする。
    git add . git commit -m "Add VCN and base code" git push -u origin main
⚠️ つまずきやすいポイント
  • git pullで「refusing to merge unrelated histories」と出たら、--allow-unrelated-historiesの付け忘れ。git pushが「rejected」になる場合は、先にgit pull origin main --allow-unrelated-historiesを実行していない可能性が高い。
  • 初回のgit push時、ブラウザが自動で開いてGitHubへのログインを求められることがある（Git Credential Managerという仕組み）。エラーではないので、そのままブラウザ側でログイン・許可すればよい。

時間配分学習内容
30分CloudWatch／CloudTrail／AWS Config／SNS通知
25分AWS Backup／障害検知／ログ・監査／運用上の可視化

比較・判断軸（20分）
  • 総合設計：要件 → 制約 → 候補サービス → 比較 → 適切なサービス選択 → アーキテクチャ
  • セキュリティ・可用性・高性能・コスト・運用負荷を同時に考え、単一サービスではなく複数サービスを組み合わせて設計する

典型要件
  • 障害を早期検知し、通知したい → CloudWatch + SNS等
  • APIやコンソール操作などの監査証跡を残したい → CloudTrail
  • AWSリソースの設定変更やコンプライアンスを確認したい → AWS Config
  • バックアップを一元管理したい → AWS Backup
  • データベースをAWSへ移行したい → AWS DMS
  • オンプレミスとAWS間で大量のファイルを転送・同期したい → AWS DataSync
  • オンプレミス環境からS3等のクラウドストレージへ接続したい → AWS Storage Gateway
  • 大量データを物理デバイスで移行したい → AWS Snow Family
到達目標：これまで学習した主要サービスと設計判断を統合し、複数の制約を持つ要件に対して、適切なAWSアーキテクチャを説明できる状態を目指す。あわせて、オンプレミスからAWSへの主な移行・転送手段を要件から選択できるようにする。
