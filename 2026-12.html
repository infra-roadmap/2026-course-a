12月：Terraform実践

コースB：OCI限定コース（AWS資格を目指さない）

Terraformの基本操作をより実践的に理解し、Compute（コンピュート）まで含めた一連の構築ができるようにします。

💼 この月で実務的にできるようになること：terraform planの差分の読み方やtfstateの中身を理解した上で、data sourceで既存情報を参照しながらCompute環境までを一連のコードで構築・変更できるようになります。

📖 この月で出てくる用語

用語ひとことで言うともう少し詳しく
state管理Terraformの「現在の状態」を保存・確認することterraform state list等のコマンドで中身を見られる
data source既存の情報を参照する仕組み自分で作ったのではなく、OCI側に既にある情報（可用性ドメイン等）を取得して使う

WEEK 01目安 3.5h

terraform plan/apply の理解

🎯 このタスクのゴール
plan（予告）とapply（実行）の違いを、実際に差分を出して体感する。
📚 使う教材
  • Terraform公式CLIドキュメント https://developer.hashicorp.com/terraform/cli
🛠 具体的な手順
  1. PowerShell（またはコマンドプロンプト）を開く（スタートメニューで「PowerShell」と検索して起動。普段VS Codeを使っているなら内蔵のターミナル機能でもよい）。作業フォルダ（cd $env:USERPROFILE\oci-learning-log）に移動してから、以降の操作を行う。
  2. 現在の状態を確認する（基準づくり）。 11月までに、VCNとPublic/Private Subnetまでを構築済みのはず。次を実行し、No changes. Your infrastructure matches the configuration.と表示されることを確認する。
    terraform plan
    差分が出る場合は、11月のapply漏れなどが原因なので、先に解消してから進める（この月のWEEK 03でComputeを作るので、今の時点でTerraformが管理しているのはVCNとSubnetなど、ネットワーク関連のみ）。
  3. planの出力の読み方を押さえる。 planでは、各リソースの行頭の記号が「何が起きるか」を表す。
    +        新しく作成する
-        削除する
~        その場で変更する（in-place update）
-/+      削除して作り直す（replace）

最終行：Plan: ◯ to add, ◯ to change, ◯ to destroy.
        （追加◯個、変更◯個、削除◯個の予定、という意味）
    特に-/+（作り直し）は、そのリソースが一度消えるので、本番では最も注意して見る記号になる。
  4. コードを意図的に1行変更して、差分を出す。 notepad terraform.tfvarsで開き、vcn_display_name = "tf-vcn"の行をvcn_display_name = "tf-vcn-v2"に変えて保存する（11月に、VCNの名前を変数に切り出してあるため、変更はterraform.tfvarsで行う。もしmain.tfにdisplay_nameを直接書いている場合は、main.tfの値を変える）。続けて次を実行する。
    terraform fmt terraform validate terraform plan
    validateはSuccess! The configuration is valid.になること。今後、planの前にfmt→validateを実行する習慣をつける。planの結果は、次のようにVCNのdisplay_nameだけが~（その場で変更）として表示されれば正しい。
      # oci_core_vcn.main will be updated in-place
  ~ resource "oci_core_vcn" "main" {
      ~ display_name = "tf-vcn" -> "tf-vcn-v2"
        # (その他の項目は変更なし)
    }

Plan: 0 to add, 1 to change, 0 to destroy.
    作り直し（-/+）ではなく、その場の変更（~）になっていること、Subnetなどほかのリソースには差分が出ていないことも合わせて確認する。
  5. planは「予告」だけで、実環境は何も変わらないことを確認する。 OCIコンソールで「ネットワーキング」→「仮想クラウド・ネットワーク」を開き、VCNの名前がまだtf-vcnのままであることを確認する（planを実行しても、OCI側は変更されない）。確認できたら、terraform.tfvarsをvcn_display_name = "tf-vcn"に戻して保存し、terraform planでNo changes.に戻ったことを確認する（次のドリフトの体験の前に、基準の状態に戻しておく）。
  6. 「ドリフト」を体験する。 今度は、コードは何も変更せずに、OCIコンソール側だけを変更する。コンソールでVCNの詳細画面を開き、「編集」からVCNの名前をtf-vcn-manualに変更して保存する。その状態で、PowerShellで次を実行する。
    terraform plan
    コードには何も書いていないのに、次のように差分が検出される（表示は多少異なることがある）。
    Note: Objects have changed outside of Terraform
  # oci_core_vcn.main has changed
  ~ resource "oci_core_vcn" "main" {
      ~ display_name = "tf-vcn" -> "tf-vcn-manual"
    }

  # oci_core_vcn.main will be updated in-place
  ~ resource "oci_core_vcn" "main" {
      ~ display_name = "tf-vcn-manual" -> "tf-vcn"
    }

Plan: 0 to add, 1 to change, 0 to destroy.
    前半のObjects have changed outside of Terraformは「Terraformの外（コンソール）で、実際の状態が変えられていた」という検出結果、後半は「コードの状態に戻すために、これから行う変更の予告」。このように、コンソールから直接触ると、コードと実際の状態がズレる。これを「ドリフト」と呼ぶ。（補足：コードに書いていない項目をコンソールで変更しても、planに出ない場合がある。ドリフトを確実に体験するため、今回はコードに書いてある項目（名前）を変更している）
  7. applyでコード側の状態に戻す。 次を実行し、確認を求められたらyesと入力する。
    terraform apply
    Apply complete! Resources: 0 added, 1 changed, 0 destroyed.と表示されることを確認する。続けてOCIコンソールのVCN一覧を開き（画面を再読み込みする）、VCNの名前がtf-vcnに戻っていることを確認する（planは予告だけで何も変えず、applyで初めて実環境が変わる）。最後にterraform planを実行し、No changes.になっていれば完了。
⚠️ つまずきやすいポイント
  • 手順3でコードを変えたら、手順4で必ず元の値（tf-vcn）に戻す。戻し忘れると、手順5のドリフトの体験で、差分の意味が分かりにくくなる。
  • 手順3の変更でplanに-/+（作り直し）が出たら、変更した項目が違っている。cidr_blockなどを変えていないか確認する（display_nameの変更は、作り直しにならず、~の変更になる）。
  • terraform planの最初のメッセージがEnter a value:の場合は、terraform.tfvarsが読み込まれていない。作業フォルダ（oci-learning-log）にいるか、ファイル名が正しいかを確認する。
  • コンソールで名前を変えたあと、planに差分が出ない場合は、画面を再読み込みして、名前の変更が保存されているかを確認する。
✅ 成果物
🧭 到達判定
  • planの記号（+ ／ - ／ ~ ／ -/+）の意味と、最終行のPlan: ◯ to add...の読み方を説明できる
  • planは実環境を変えず、applyで初めて変わることを、実際の画面で確認して説明できる
  • コード側を変更していないのにplanで差分が出る「ドリフト」が何によって起きるか説明できる
WEEK 02目安 4.5h

state管理

🎯 このタスクのゴール
Terraformが「今何を管理しているか」を自分で確認できるようになる。
📚 使う教材
  • Terraform公式ドキュメント（State） https://developer.hashicorp.com/terraform/language/state
🛠 具体的な手順
  1. PowerShell（またはコマンドプロンプト）を開く（スタートメニューで「PowerShell」と検索して起動。普段VS Codeを使っているなら内蔵のターミナル機能でもよい）。作業フォルダ（cd $env:USERPROFILE\oci-learning-log）に移動してから、以降の操作を行う。
  2. terraform.tfstateの中身をエディタで開いて構造（JSON形式）を確認する。
  3. terraform state listで管理対象のリソース一覧を表示する。
  4. terraform state show <resource>で特定リソースの詳細を確認する。
  5. OCI CLIとも突き合わせる。 oci compute instance list --compartment-id <コンパートメントOCID>を実行し、terraform state listの内容と実際に作成されているリソースが一致していることを確認する。
  6. 「なぜstateを直接編集してはいけないか」を理解する。 terraform apply実行後にフォルダ内へ自動生成されるterraform.tfstate.backup（1つ前の状態のバックアップ）の存在を確認し、これが「stateファイルは壊れやすく、手で編集するとコードと実際のリソースの対応が壊れる」ことへの保険であることをメモにまとめる。
⚠️ つまずきやすいポイント
  • tfstateには接続情報などの機密が平文で入ることがあるため、Gitには絶対に含めない（11月にすでに.gitignoreへ追加済みのはず）。
🧪 手動リソースのTerraform管理化（import）
Terraformを使わずに手動で作ったリソースをterraform importでstateに取り込み、コードと実際のリソースを一致させる。
  1. 手動でリソースを1つ作る。 OCIコンソールから、Terraformではまだ管理していない新しいNSG（例：manual-test-nsg）を1つ手動で作成する（Ingressルールは動作確認用にTCP 8080番を1つ追加する程度でよい）。
  2. コード側に受け皿を用意する。 main.tfに、作成したNSGと同じ内容（名前・所属VCN等）を指すresource "oci_core_network_security_group" "manual_test" {...}ブロックを追加する（この時点ではまだstateに紐づいていない）。
  3. importする。
    terraform import oci_core_network_security_group.manual_test <NSGのOCID>
    NSGのOCIDはOCIコンソールの詳細画面からコピーする。
  4. 一致を確認する。 terraform planを実行し、差分が（ほぼ）出ないことを確認する。差分が出た場合は、コード側の設定値が実際のリソースと食い違っているので、表示された差分を1つずつ実際の値に合わせて書き直す。
  5. 後片付けする。 確認できたら、手順2で追加したresource "oci_core_network_security_group" "manual_test" {...}ブロックをmain.tfから削除する。terraform planを再度実行し、このNSGが削除対象として表示されることを確認したうえで、terraform applyを実行して実体を削除する。コードとstateの両方から消すことで、次回以降のplanで再作成対象として残らないようにする。学習用に増やしたリソースはその都度整理する習慣をつける。
⚠️ つまずきやすいポイント
  • -targetオプションは、依存関係を無視するものではなく、指定したリソースを中心とした部分的なplan／apply／destroyを行うためのオプション。指定したリソースが依存する他のリソースは通常どおり考慮されるが、対象範囲を絞る分、コード全体の依存関係と実際に適用された状態がずれやすくなる。特にdestroy -targetで実体だけを削除すると、コードにはresourceブロックが残ったままになり、次回のplanで再作成対象として検出されてしまう（今回の後片付けでコードからブロックごと削除したのはそのため）。通常の運用では-targetなしのterraform plan／apply／destroyを基本とし、-targetは障害対応や復旧作業など、限定的な用途に絞って使う、という位置づけで覚えておく。
✅ 成果物
🧭 到達判定
  • tfstateを直接編集してはいけない理由を説明できる
  • terraform importで手動作成したリソースをTerraform管理下に置く流れを説明できる
WEEK 03目安 3.5h

data source、Computeまで含めた一連の構築

🎯 このタスクのゴール
既存の情報（可用性ドメイン）を参照しながら、Compute（コンピュート）インスタンスまでコードで構築する。
📚 使う教材
  • Terraform公式ドキュメント（Data Sources） https://developer.hashicorp.com/terraform/language/data-sources
🛠 具体的な手順
  1. PowerShell（またはコマンドプロンプト）を開く（スタートメニューで「PowerShell」と検索して起動。普段VS Codeを使っているなら内蔵のターミナル機能でもよい）。作業フォルダ（cd $env:USERPROFILE\oci-learning-log）に移動してから、以降の操作を行う。
  2. data "oci_identity_availability_domains" "ads" {}のようなdata sourceを定義し、可用性ドメインの一覧を取得する。
  3. Terraform apply前に、10月から使い続けている手動のCompute（Public Subnet、VM.Standard.E2.1.Micro）をOCIコンソールから削除する。 このあとTerraformで作成するComputeも同じE2.1.Microを使うため、手動作成分を残したままだと、テナンシー全体でのE2.1.Micro上限（最大2台）に抵触しうる。先に手動分を片付けてからapplyする。
  4. 取得した値を使ってoci_core_instanceリソースを記述する（subnet_idには11月に構築したTerraform管理VCNのPublic Subnetを指定する）。Shapeは、直前に削除した10月の手動Computeと同じVM.Standard.E2.1.Microにする。これにより「手動で作ったComputeを、同じ内容のままTerraformコードとして再構築する」という移行の流れを体験する。
  5. terraform fmtとterraform validateでコードを整形・検証してから、terraform applyでVCN〜Compute（コンピュート）までを一連の実行で構築できることを確認する。
✅ 成果物
🧭 到達判定
  • data sourceで取得した値を使ってComputeを構築できる
  • 手動作成分を先に削除してからapplyする必要がある理由を説明できる
WEEK 04目安 3h

Terraformコード拡張演習＆振り返り・学びメモ作成

🎯 このタスクのゴール
WEEK03で構築したCompute環境をvariableで拡張する小演習を行い、手を動かした状態のまま10〜12月をふりかえって自分の言葉で短くまとめる。公開記事を書くことが目的ではなく、「振り返って言語化する」こと自体が目的。
📚 使う教材
  • study-notesリポジトリ（9月に作成済み）。使い慣れたツール（Notion等）があればそちらでもよい https://github.com/
🛠 具体的な手順
  1. 作業用のbranchを切る。 11月に続き、変更はmainに直接コミットせずbranch上で行う。
    git checkout -b feature/second-instance
  2. 拡張演習：WEEK03で構築したCompute（コンピュート）環境に、variableを使って2台目のインスタンスを追加する（display_nameは1台目と別名にする）。2台目も同じVM.Standard.E2.1.Microとし、1台目と合わせてE2.1.MicroのAlways Free上限（テナンシー全体で最大2台）にちょうど収める。terraform fmt→terraform validateで整形・検証したあと、terraform planで追加分の差分だけが出ることを確認してからapplyする。
  3. 動作確認ができたら、Always Free枠を使い切らないよう2台目はterraform destroyで削除しておく（variable定義自体はコードに残してOK）。
  4. branch上でcommitし、pushする。
    git add . git commit -m "Add second instance variable" git push -u origin feature/second-instance
    このbranchのPull Request作成・レビュー・mainへのmergeは、1月以降にあらためて扱う。
  5. この1ヶ月でつまずいた点を3つ書き出す。
  6. 「①今週学んだこと ②つまずいた点 ③来週への持ち越し」の3つの見出しで、5〜10行程度の箇条書きメモを作る（文章として整える必要はない）。study-notesリポジトリに2026-12-terraform-review.mdとして保存し、pushする。
⚠️ つまずきやすいポイント
  • 「読める記事」に仕上げようとすると重くなるので、箇条書きメモで十分。公開は目的ではないので、体裁を整えることに時間をかけすぎないこと。
